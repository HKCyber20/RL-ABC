## 1. 今日目标与预计时间

预计：**120–170 分钟**。

- 把任务范围、输入、动作、控制频率和成功判据冻结为可测试合同。
- 确定 full 与 low-resource 两档实现，但保持同一核心问题。
- 建立变更控制，避免结果后修改目标。

## 2. 今日知识点及其在 VLA 中的作用

最终 spec 是所有代码、数据和评估的共同真相；没有冻结合同，成功率和可复现性都无法比较。

## 3. 必要概念、公式、形状与数据流

- 策略接口：`π(o_t:[B,3,H,W], l:[B,L], s_t:[B,D_s]) → a_t:[B,D_a]` 或 action chunk `[B,H_a,D_a]`。
- 动作合同逐维记录 name、unit、frame、range、control_hz、absolute/delta、gripper 语义；轻量环境可降维，但要写清与 7D 操作动作的映射/差异。
- 成功判据必须可程序化，例如目标在容器内连续 N 步、无安全违规且在最大步数内完成。

## 4. 分步骤学习内容

1. 用一句话冻结问题和不做范围。
2. 写输入/输出 schema、闭环时序与动作合同。
3. 定义 ID/OOD split、主指标、辅助指标和失败分母。
4. 建立 spec 变更日志规则：只能修 bug，不因结果改阈值。

## 5. 必做作业

- 提交 FINAL_SPEC.md。
- 附 12 项验收检查与机器可执行断言映射。
- 让一个未看过项目的人按 spec 复述输入、动作和成功条件，记录歧义并修正。

## 6. 作业输入、预期输出与验证方法

| 项目 | 内容 |
|---|---|
| 输入 | 前 11 周产物、可用仿真环境与资源清单。 |
| 预期输出 | spec 包含任务、输入 shape、动作语义、频率、horizon、reset、成功/失败、split、指标、资源档和非目标。 |
| 验证方法 | 逐字段对应到代码配置位置。；用 3 个边界场景判定成功/失败。；锁定 spec hash 并在后续 manifest 记录。 |

本周“预期”不能替代最终核心闭环实测；需要大模型/GPU 的 OpenVLA 部分可用明确标注的 CPU/mock dry-run。

## 7. 提交内容与固定格式

```markdown
# W12D01 提交

- 实际用时：记录分钟数
- run/result id：记录可追踪标识
- 证据等级：真实轻量/完整仿真、真实 OpenVLA、OpenVLA mock dry-run（逐项说明）

## 冻结合同与设计
记录 spec/config/data/checkpoint hash 及关键 shape、单位和 frame。

## 实际产物

## 复现与验证证据

## 失败、限制与补救
区分观察、推断和假设，给最小补救验收标准。

## 自测/答辩答案
逐题作答。
```

## 8. 评分与验收标准

| 评分项 | 分值 | 得分条件 |
|---|---:|---|
| spec/概念/shape | 20 | 输入、动作、闭环和版本合同准确 |
| 实际项目产物 | 25 | 文件完整，来源与 hash 可追踪 |
| 复现与验证 | 25 | 实际命令、退出码、重跑/重算证据充分 |
| 泛化/失败/OpenVLA | 20 | 证据边界清楚，能诊断并解释接入 |
| 复盘与答辩 | 10 | 限制诚实，回答自测并给补救 |
| **总分** | **100** | **80 分通过** |

硬门槛：动作缺单位/frame、成功需人工主观判断，或结果后可随意改阈值，不得通过。

## 9. 常见错误与排查提示

- “抓取成功”没有持续时间/容差。
- full 与 low-resource 改成两个完全不同问题。
- 未定义 simulator crash 的计数。
- 先核对 spec/config/data/checkpoint/result hash、seed、stats key、动作单位/frame，再解释性能。
- 不得把手写 outcome、mock OpenVLA 输出或预期命令包装成真实闭环/模型结果。
